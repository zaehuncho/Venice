### 2. “Triangle+Square, X gets stuck” — **needs changes; console cause unproved**

The cited chord is **not** a local Cross-down: Chiaki local log `:10852-10881` records `21:17:48.499 btn=12` (Triangle+Square), `21:17:48.557 btn=4`, and `21:17:48.571 btn=0`, with local history accepts. The earlier Cross press/up at `:10734-10753` is `21:17:43.072 btn=1` → `.177 btn=0`; the up has primary, twin, and echo accepts by `.181` (only a 4 ms span). The chord's Square-up has primary/twin at `.571/.575`; its earlier Triangle-up has three copies by `.571`. These records refute a missing **local** release for those events, not a console hold. The owner-reported later Cross tap burst warrants video/remote-state correlation rather than assuming this chord caused it.

The path not visible to those logs is the PS5/game receipt and ordering of **Feedback History**. `lib/src/feedbacksender.c:850-895` formats button edges as history; periodic Feedback State omits buttons (`:659-700`), and equal-state launcher keepalives do not create new history (`:179-195,1204-1216`; `native_orion/src/OrionInputClient.cpp:470-491`). `local_udp_accept` explicitly logs `console_ack=0` (`feedbacksender.c:716-732`). While owned, physical/SDL input is deferred (`:198-210`; `gui/src/streamsession.cpp:1312-1316,1386-1403`), so it is not an independent repair producer. A dropped/reordered set of up-history packets can therefore leave a console-side held button with no new up edge even while local ACKs and keepalives look healthy. The nominal 40 ms echo is conditional on a quiet queue (`feedbacksender.c:309-320`) and can be expedited by subsequent input (`:290-293,344-350`), so its spacing is not guaranteed; the cited Cross up's three local copies were bunched into 4 ms. Conversely, each later distinct tap generates more history (the sender retains the last four events at `:816-817`); one lost release by itself does **not** explain a persistent hold through the whole burst. The contemporaneous native health line has `abandons=0` (`logs/orion_native.log:19903`); the trigger-release split at `OrionInputClient.cpp:427-450` does not generate this pure digital chord. No evidence here proves loss, ordering failure, or a game-state cause.

**Required fix/test:** design a released-button path that eventually reasserts UP while the current owned state remains up, without letting a delayed UP overtake a newer DOWN; the present same-state keepalive is not that path. Run a real Windows-pipe + fork harness that drops and reorders primary/twin/echo history packets while maintaining a model of console button state; assert eventual neutral after every release, soft drop, ABANDON, dead-man, and ownership handoff. On the owner rig, correlate packet sequence and controller-on-console video/overlay through the burst. A pure local-ACK test cannot close this gate because it has no console acknowledgement.
