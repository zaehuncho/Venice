## Findings (LOW → CRITICAL)

### CL3-F4-001 LOW: the release-oracle path still lacks the dev-offset fence (CL2-P6-003, oracle half)
- **Tier:** source-confirmed; the production containment is package-string.
- **Component:** `AutomationEngine.cpp` `flushExpiredReleaseOracles` (~15827-15890). It refuses FF-displaced oracles (`onsetFfMs != 0`), but it has no `devFireOffsetArmed_` check. The banner path has one (`:15563`).
- **Precondition:** a dev build with `ORION_DEV_FIRE_OFFSET_SWEEP` armed. This is the owner's own experiment launcher.
- **Failure path:**
  1. A deliberately displaced shot parks an oracle.
  2. The oracle is consumed.
  3. The trim moves and is persisted to `learning.json` `banner_lead_trim_by_type`.
- **Impact:** it contaminates the owner's experiments and persisted trim. It is **not reachable in production**: `ORION_DEV_FIRE_OFFSET_SWEEP` is absent from the package `AutomationCore.dll` and `OrionNative.exe` (ASCII and UTF-16 both 0), while the dev `AutomationCore.dll` contains it (control = 1).
- **Repro:** `grep -c -a ORION_DEV_FIRE_OFFSET_SWEEP <pkg>/AutomationCore.dll` → `0`; the dev DLL → `1`; exit 0. Source: `grep -n "dev_offset\|devFireOffsetArmed_" AutomationEngine.cpp` shows no hit in 15827-15900.
- **Fix:** add `if (devFireOffsetArmed_) { log ORACLE used=0 reason=dev_offset; continue; }` next to the `onset_ff_displaced` refusal.
- **Closure test:** extend `devFireOffsetArmedRefusesBannerTrimEvidence` with an oracle-only miss sequence. Assert no trim delta and a `reason=dev_offset` line.

### CL3-F4-002 LOW: about 70 timing environment knobs are still honoured by the production engine

  - `ONSET_FF_*`
  - `LEAD_FLOOR`/`BIAS`

  - late carry

### CL3-F4-006 MEDIUM: `learning.json` semantic garbage is still accepted (M-12 still open)
- **Tier:** source-confirmed. The live impact is a hypothesis.
- **Component:** `AppConfig.cpp:2178-2320` `loadLearningObject`.
  - These values are accepted as any finite double: `bias_pct`, `ema_fill_per_frame`, `learned_latency_ms`, `global_appear_to_tip_ms`, `global_hold_to_release_ms`, `probe_spawn_offset_ms`, `global_rise_velocity_pct_ms`.
  - These per-type maps are also unbounded: `shot_type_learned_offset_ms`, `shot_type_feedforward_ms`, `shot_type_meter_to_release_ms`, `shot_type_appear_to_tip_ms`, `shot_type_latency_ms`, `shot_type_velocity_prior_pct_ms`, `shot_type_rtt_baseline_ms`.

  Only the phase slots, `no_meter_hold_by_type` and `banner_lead_trim_by_type` are band-checked. `bias_pct` has no writer in the product (only `AppConfig.cpp:1133` round-trip) but feeds the live `processHolding` aim target (`:11298-11309`, `clampPct(100 + bias)`). The `.bak` rotation (`:1260`) copies any *syntactically* valid file, so garbage rotates into "last good".
- **Precondition:** a bit-rot, hand-edited or buggy-writer `learning.json` that is still valid JSON. `learning.json` has no signature. Syntactic corruption is handled: `learningRecoversFromBackupWhenCorrupt` and `learningWithoutBackupQuarantinesAndDefaults` PASS.
- **Failure path:** for example, `"bias_pct": -60` moves the processHolding aim target to 40% fill. Whether that reaches the tip-phase-solo fire in the shipped configuration was **not** proven: no scratch build was allowed while StrictSecurity runs.
- **Impact:** a potential persistent early/late shift with no warning. `actuation_lead_ms=0` in `settings.json` is **not** such a case. It reads as "not configured" (auto seed), and `0 + user_set=true` fails the user-lead gate (`:14558-14564`, `< actuationLeadMinMs`), so it waits for authority rather than firing at lead 0 (source-confirmed).
- **Fix:** band every learning field at load, using the same plausibility the learners enforce. Refuse to rotate a file into `.bak` unless it passes the semantic check.
- **Closure test:** a fixture set with 1e300, −1e9, and negative or zero clocks per key, asserting the defaults are applied and `.bak` is not overwritten by the bad generation.

### CL3-F4-007 MEDIUM: the meter-blind warning and the DETECTION UNAVAILABLE latch cannot trip for Square presses in METER mode (M-13 / CL2-P9-001 still open for its main case)
- **Tier:** observed-dev on a pre-latch launcher, plus source-confirmed on the candidate. **Fire safety is fail-closed:** no silent fire.
- **Component:**
  - `OrionAppController::observeMeterBlindness` (`OrionAppController.cpp:11711`) is called from the telemetry path with `shot_.physicalShotEpoch` (`:2995`). The streak advances only when that epoch changes.
  - `ShotContext::physicalShotEpoch` is assigned **only** in `AutomationEngine::beginShot` (`AutomationEngine.cpp:7123`).
  - In METER mode a meterless Square press never begins a shot. It stays in `pendingSquarePhysicalEpoch_` and ends as `SHOT NOT OWNED: reason=press_unanswered_no_meter … backstop=green_window_priority`. So the epoch the detector sees never changes, the streak never reaches `kMeterBlindStreakTrip_ = 3`, and `setDetectionUnavailable(true)` is never called.
- **Preconditions:** a 2K patch, the wrong in-game style or colour, or a dead reader, while in METER mode.
- **Failure path:** the bot silently stops timing shots. The player's own presses pass through, which is correct. But the customer gets no "meter not detected" warning and no explicit unavailable state, which the P9 lane requires.
- **Live control (observed-dev):** in `session_20260922_210220` the in-game meter was Pill while Venice read Arrow2. There were 80 presses in 2m41s:
  - outcomes: `unanswered` 73, `disarmed` 7, `release_ms` set 0
  - `first_sight_fill` never ≥ 0
  - log window 02:02:19-02:05:44Z: `SHOT NOT OWNED` 7 lines, `PRECISE FIRE ARM|LIVE TIP PRIORITY|ORACLE` 0, `METER BLIND|DETECTION UNAVAILABLE` **0**

  The METER BLIND advisory code has existed since `7d19686` (08-09), and `appendLog` lines do reach `orion_native.log` (29 hits for other appendLog text). That build predates the 09-23 latch, but the latch reads the same epoch source.
- **Side defect:** the recovery (`observeBotOwnership`) counts any new epoch in `Holding`/`GreenWindow` as "owned". A Go-To stick push enters `Holding` with `release_reason=await_meter` and no meter (`gotoMeterWaitBlindFiresAtSafetyCapNeverHangs`). So two meterless Go-To pushes would clear the latch and the warning. The latch copy ("blind timer shots are OFF until…") also describes a backstop that `greenWindowPriority` already keeps permanently off.
- **Fixture evidence that fire stays closed:** `OrionNativeTests.exe` with `meterModeNeverAnswersAnUnownedPressBlindly` (6 rows), `meterModeNeverBlindReleasesAnyGesture`, `meterVisionPrioritySuppressesDefaultBlindBackstop`, `meterBlindBackstopStandsDownWhileDetectionUnavailable`, `gotoNoMeterBlindFires`, `gotoStalePhantomBlindFiresAtNoMeterCap` and `feedforwardReleasesBlindWhenMeterInvisible` → PASS. Despite the names, the Go-To and feedforward tests assert `no_meter_abort`, `shotsReleased()==0` and a physical pass-through. Overall: **22 passed, 0 failed, 1 skipped** (`meterStyleLockRejectsOtherProfiles`: OpenCV not enabled); exit 0.
- **Fix:** feed the detector from the engine's press epoch, for example a `pressUnansweredNoMeter(epoch)` signal emitted at the `SHOT NOT OWNED … press_unanswered_no_meter` terminal. Recovery should require a genuine vision-owned shot (`meterDetected && lastSampleGenuineAccept`), not bare `Holding`. Reword the latch copy.
- **Closure test:** a controller-level fixture with 3 meterless METER-mode Square presses, asserting `meterBlindWarning` and `automation_.detectionUnavailable()`. Two meterless Go-To pushes must not clear it; 2 vision-owned shots must clear it.

### CL3-F4-008 MEDIUM: FF-displaced releases still train the press→tip / no-meter hold learners (M-25 / CL2-P6-001 still open, observed today)
- **Tier:** observed-dev (today) plus source-confirmed on the candidate.
- **Component:** `AutomationEngine.cpp`:
  - `:22306` `recordNoMeterHoldObservation` gate
  - `:22372` PRESS-TIP `accepted`

- **Precondition:** the shipped default FF (gain 0.2, clamp 10, one-sided) applies a displacement of ≥ 2 ms.
- **Failure path:**
  1. A one-sided (earlier-only) displacement rides the release.
  2. It feeds `no_meter_hold_by_type` (persisted in `learning.json`) and `press_anchored_tip_ms` (`settings.json`).
  3. It also feeds the persisted per-type velocity prior.

  Every leaked sample is biased in the same direction.
- **Observed today (`session_20260923_120043`, dev launcher):** all **6/6** `ONSET FF: reason=applied` epochs (20, 35, 37, 39, 43, 44; applied −5.47/−10/−10/−10/−10/−5.19 ms) have a matching `PRESS-TIP OBSERVATION … accepted=1`. Extract: `claude-F4/session_log.txt`.

- **Fix:** add `&& lastReleaseOnsetFfMs_ == 0.0` (via the meter-cap copy of the release's displacement) at `:22306`, `:22372`, `:13357`, `:13364` and `:13404`. Keep the 2 ms floor so sub-floor shots still train.
- **Closure test:** a displaced-release fixture asserting `accepted=0` and no `noMeterHoldLearned`/`velocityPriorUpdated` emission. An undisplaced control must still be accepted.

### CL3-F4-009 MEDIUM: calibration Cancel can pin a wrong user-set lead (M-26 regressed, not closed)
- **Tier:** source-confirmed, plus a line-for-line model reproduction (no product binary exercised).
- **Component:** `OrionAppController.cpp:9346-9410`. `beginLeadCalibration` stores `leadCalStartLeadMs_ = actuationLeadMs()` (0 on an Auto install) and not the `user_set` flag. When `shots > 0` and not locked, `cancelLeadCalibration` calls `setActuationLeadMs(leadCalStartLeadMs_ > 0 ? start : actuationLeadMs())`. `setActuationLeadMs` clamps to [150, 800] and forces `actuationLeadUserSet = true`.
- **Precondition:** this is a normal first-run path. The card tells a new install "Not set yet — 10 to 15 open shots find this rig's own number". The customer then taps a verdict and presses Cancel.
- **Failure path (model output, `claude-F4/calcancel_model.py`, exit 0):**

  ```text
  Auto install, GOOD then Cancel        before=(0,user=False) after=(150,user=True)  [log says lead back at 0 ms]
  Auto install, LATE then Cancel        before=(0,user=False) after=(320,user=True)  [log says lead back at 320 ms]
  Auto install, EARLY,LATE then Cancel  before=(0,user=False) after=(290,user=True)
  User 280, LATE then Cancel (control)  before=(280,user=True) after=(280,user=True)
  Auto install, SKIP only then Cancel   before=(0,user=False) after=(0,user=False)  [unchanged]
  ```

  A measured-seed install (lead > 0, `user_set=false`) keeps its value but flips to `user_set=true`, which ends the auto seed for good.
- **Impact:** the worst case pins a 150 ms user lead where the rig needs about 270 ms. That is about 120 ms too little lead, so every live-tip shot fires late (late = miss on 2K27), and the lead stays until the customer moves the slider. The activity line says "the lead is back at 0 ms", which is false. It also calls `resetBannerTally`. There are no tests for `cancelLeadCalibration` in the repo.
- **Fix:**
  1. Snapshot `{actuationLeadMs, actuationLeadUserSet, actuationLeadBySource entry}` at begin.
  2. On Cancel, restore that exact tuple through a path that can write `0 / user_set=false`, for example a `restoreActuationLeadProvenance` helper, not `setActuationLeadMs`.
  3. Log the restored value and provenance.
- **Closure test:** a controller-level test (or a `LeadCalibrationController` extraction) that covers:
  - Auto → GOOD → Cancel, and Auto → LATE → Cancel, asserting `(0, false)`
  - seeded 270/false → LATE → Cancel, asserting `(270, false)`
  - user 280/true, asserting `(280, true)`
  - lock/Done keeps the calibrated value
