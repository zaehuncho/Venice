## Findings (LOW → CRITICAL)

### CL3-F6-001 — LOW — Owner TOTP step-up is bypassed on the owner-role staff-token path
- Tier: source-confirmed. Candidate `59129e5` / rc1 (`api.zaeorion.com` backend, not in package).
- Component: `backend/lambda_function.py` `resolve_owner()` (3481–3512), `handle_admin_config` `totp_disable` (4819–4825), `rotate_admin_secret` (4827–4842).
- Preconditions: `owner_totp_required=true`; attacker holds a valid **owner-role** staff bearer token + its bound `X-Machine-Id`; source IP on the owner allowlist.
- Path: `resolve_owner` enforces `owner_totp_ok(event)` **only** on the break-glass `x-orion-admin-secret` path (3494–3501). The alternate owner-role staff-token path (3503–3511) authenticates on bearer + role alone and sets `_actor` with **no TOTP check**. `totp_disable` / `rotate_admin_secret` then run with no fresh code. So a stolen owner-role staff token can turn 2FA off (and rotate the admin secret) without ever possessing the TOTP secret — the exact property M-18's "step-up code on disable" was meant to guarantee.
- Impact: defeats the purpose of TOTP as a second factor against a compromised primary owner credential on the staff-token path. Bounded: needs a live owner-role staff token, its machine binding, and an allowlisted IP; the break-glass path is correctly protected.
- Repro (source, fixtures): none run for this specific path — the passing `test_a5_fixup.py` (15/15) and `test_staff_rbac.py`/`test_admin_v2.py` (in the 169-pass run) do not assert a TOTP challenge on `totp_disable` via an owner-role staff token. Fixture reproduction is the closure test below.
- Fix: in `handle_admin_config`, require a valid `x-orion-admin-totp` for `totp_disable` and `rotate_admin_secret` whenever `owner_totp_secret()` is enrolled, regardless of which authenticator resolved the actor; audit `owner.totp_denied` on failure.
- Closure test: backend fixture — enrolled+required TOTP, owner-role staff token, `action=totp_disable` with no/invalid `x-orion-admin-totp` → asserts 403 `totp_required`/`invalid_totp`, config unchanged, audit row written; and with a valid code → succeeds.

### CL3-F6-002 — LOW/MEDIUM — Stripe webhook has no edge-level event-id dedup; idempotency rests entirely on backend order_id / revoke-state
- Tier: source-confirmed (Worker), fixture (backend behaviour idempotent).
- Component: `website/src/worker.js` `processStripeEvent`/`stripeWebhook` (718–830); `backend/lambda_function.py` `handle_bot_provision` order marker (2690–2693), `handle_bot_chargeback` (5051–5095).
- Path: `stripeWebhook` verifies the HMAC (`verifyStripeSignature`, 367–378: SHA-256, constant-time, `±STRIPE_TOLERANCE_SECONDS`) then processes with **no `event.id` replay store**. Idempotency of provision is delegated to backend `order_id = stripe:checkout:<id>` / `stripe:invoice:<id>` dedup; refund/dispute calls `/api/bot/chargeback`, which does an unconditional `update_item revoked=true`.
- Impact: functionally safe — provision replay hits the order marker; chargeback replay re-sets an already-revoked key (same terminal state, no lease re-mint). Residual: a replayed `charge.refunded`/`dispute.created` re-fires `owner_alert` + a fresh `webhook.chargeback` audit row and re-runs role reconciliation each time (alert/audit noise, wasted Stripe API reads); a replayed cancellation likewise re-audits. This is the still-open part of M-23 ("replay is not idempotent") narrowed to *observability/side-effect* idempotency, not entitlement corruption.
- Repro: `node --test tests/worker.test.mjs` → **47/47 pass, exit 0** (signature/partial-refund/identity guards exercised); backend `test_webhooks.py` in the 169-pass run. No test asserts single-alert on duplicate `event.id`.
- Fix (optional for beta): dedup on `event.id` at the Worker (KV/D1 seen-set) or make `owner_alert`/audit on chargeback conditional on an actual state transition (revoked was false → true).
- Closure test: deliver the same signed `charge.refunded` twice → assert one revoke, one alert, one audit row.
