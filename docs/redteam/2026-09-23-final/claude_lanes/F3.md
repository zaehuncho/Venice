## Findings (LOW → CRITICAL)

### [CL3-F3-007] LOW: session readiness and failure messages name the configured console IP, not the address the launch actually used
- **Evidence tier:** observed in logs. Candidate source `59129e5`.
- **Component:** `remote_play_client.py` (readiness and failure message built from `self._config.console_ip`, around lines 1940-1950); the sidecar `start_stream` line.
- **Preconditions:** the console address drifts. On the owner's rig this happens on every launch since 00:58Z.
- **Failure path:**
  1. Discovery retargets the launch to `.126`.
  2. `Sidecar: start_stream: Chiaki console input session ready (console_ip=192.168.137.81)` is then logged (`orion_native.log:207, 2607, 10508, 15386, 16783, 23403, 37003`), and the failure text says `Remote Play input session to 192.168.137.81 did not become ready` (`:23043`).
  3. The retry in the same second reached a console that answered `already in use`, which a silent `.81` cannot produce.
- **Impact:** support is sent to the wrong address. The same area as M-34, from the observability side.
- **Reproduction:** `grep -a -n "CONSOLE ADDRESS DRIFT\|session ready (console_ip" logs/orion_native.log` gave 11 drift lines and 7 `ready (console_ip=…81)` lines. Exit 0.
- **Fix:** log and message the effective target (plus the configured one when they differ), and persist the drift correction only through the settings-signing path.
- **Closure test:** a unit test with a fake discovery drift asserts that the ready and failure strings contain the effective IP.

### [CL3-F3-006] LOW: telemetry-silence aging during the sidecar stop→start gap has no event-loop fixture; the one observed trip killed a freshly connected session
- **Evidence tier:** observed on an older launcher; the current fix is source-confirmed only.
- **Component:** `native_orion/src/RemotePlaySession.cpp` (`stopSidecar` at line 2840 does not clear `haveTelemetry_`/`telemetryArmed_`; start re-arms at 2297-2300); `SidecarWatchdog.h:44-60`; `OrionAppController.cpp:6500-6560`.
- **Failure path (observed):**
  1. At 02:29:18.148Z, `Watchdog trip: Capture transport failed (transport age 10280 ms …; detector frame age 10280 ms, pixel age 10280 ms)`. All three ages are identical, which is the silence-aging signature.
  2. 10.28 s before the trip is 02:29:07.87, the retiring sidecar's last record. The new sidecar had started at 02:29:11.847, so the silence clock was inherited across the restart.
  3. The trip restarted a session that had reached `streaminfo` 0.5 s earlier (child log `21-29-16`, 21:29:17.651). Connect took 27.9 s in total.
- **Current source:** re-arming on start (CL-006 r2) resets the clock, so this exact sequence should not recur. The stop→start gap still ages from the old record, and nothing but timing margin prevents a trip there: the 5 s graceful deadline plus the 3 s capture-card delay is about the 8 s threshold plus 1.5 s of confirmation.
- **Impact:** a false transport restart during reconnect. Automation stays disarmed, so the cost is latency, not a misfire.
- **Reproduction:** the log lines cited above (`orion_native.log:23123`). No fixture exists: the only test is the helper test `OrionInputProtocolTests.cpp:1770-1784`.
- **Fix:** clear `haveTelemetry_` and disarm in `stopSidecar()`; key the watchdog's cold-start grace to any sidecar start, not only to watchdog-originated restarts.
- **Closure test:** a Qt event-loop fixture with the fake sidecar: stop A, delay the start by 7.5 s, start B without telemetry for 15 s. Assert no trip, then one trip after B's 20 s grace plus the threshold.

- **Evidence tier:** observed in the real bundle, plus a fixture reproduction.

### [CL3-F3-002] MEDIUM: every normal capture-card close is classified abnormal and pinned; four normal closes evict a real incident bundle
- **Evidence tier:** observed in the owner's session with the candidate fork `1f659a46` (dev launcher), source-confirmed, and a fixture reproduction.
- **Component:** `orion_exit_evidence.py:23,101-114,169-202`; `remote_play_client.py:2186-2217`; native shutdown order; fork `orioninputbridge.cpp` fatal path. This is CL2-P2-005 still open, now with a consequence.
- **Failure path (observed at 17:23:14Z):**
  1. `Owned input cleanup` closes the input pipe while the fork still owns it (native `.139–.142`).
  2. The fork logs `fatal_local_delivery_fault … reason=owner_pipe_disconnected` and `Orion exit_path: source=orion_bridge_fatal`.
  3. The fork then sends a proper `StreamConnection sending Disconnect` and logs `Session has quit` (`.149`), so the console *is* cleanly disconnected.
  4. The ledger has **no `window_close` request**, so `hwnd` was 0 in capture-card mode and WM_CLOSE was never posted. Yet the reason is recorded as `stop_force_after_graceful_budget` (at `.1545Z`, 5 ms after `Session has quit`), followed by `stop_force_fallback`.
  5. The child is killed before it can write `Orion process_exit` (`child_final_line=false`). The observed exit is `classification="forced_by_parent", exit_code=1`, and a ~2.8 MB incident bundle is written.
  6. Even if the child had exited 0 unprompted, the `orion_bridge_fatal` tail classifies it `child_fault`.
- **Impact:**
  - Every ordinary close creates an "incident".
  - `_MAX_BUNDLES = 4` keeps only the newest four, so after four normal closes the genuinely abnormal bundle (the reason AUD-A3-002 exists) is gone.
  - Support sees `forced_by_parent`/`child_fault` for normal sessions and cannot separate them from real faults. The native log says `Sidecar shutdown completed gracefully` while the child was force-killed.
- **Reproduction:** `.venv\Scripts\python.exe -B C:\Users\aaron\AppData\Local\Temp\claude-F3\f3_exit_evidence_fixture.py` gave:
  - `CASE1 normal close forced (cc-mode today): forced_by_parent`
  - `CASE2 normal close child exits 0 unrequested: child_fault`
  - `CASE3 real incident: external_or_runtime_unknown`
  - `after 3 normal close(s): … incident_retained=True`
  - `after 4 normal close(s): bundles=4 incident_retained=False`
  - Exit 0.
- **Field evidence:** `%APPDATA%\Chiaki\Chiaki\log\orion_parent_termination.jsonl` (5 records, all from pid 50016) and `incidents\1790184194418699100-g1-p50016\manifest.json` (`"classification": "forced_by_parent"`).
- **Fix:**
  1. On an intentional stop, send a MustDeliver ownership release (`own=0`) before closing the pipe, and have the fork log `owner_released_then_closed` at INFO (CL2-P2-005).
  2. Record the parent's own intent (`intentional_session_end`) before the pipe close.
  3. Give the child a bounded wait for its clean exit (it had already quit its session) before forcing.
  4. Classify an intentional stop with a clean `Session has quit` as `clean_intentional`, and never pin it.
  5. Pin abnormal bundles separately from the rolling count.
  6. Rename the reason to `stop_force_no_window` when no WM_CLOSE was posted.
- **Closure test:** five start→play→quit cycles in capture-card mode give zero `fatal_local_delivery_fault` lines, zero new incident bundles and five `clean_intentional` records. Then inject one abrupt kill followed by 10 normal closes; the abrupt bundle survives.

### [CL3-F3-001] MEDIUM: the default Python suite force-kills any live OrionStream on the machine; this very likely caused the 02:28:59Z "unexplained" exit
- **Evidence tier:** source-confirmed, a fixture reproduction (with fakes), and a time-correlated field log. The causal link to pid 60604 is a strong hypothesis with no initiator record.
- **Component:** `tests/test_remote_play_client_stale_sweep.py:145-155` (`test_real_snapshot_and_sweep_are_cheap_with_nothing_to_kill`); `remote_play_client.py:689-…` (`terminate_chiaki_processes`), which kills machine-wide by image name with `TerminateProcess(h,1)`. The test is not marked `slow` and runs in every broad `pytest tests` gate (the candidate sheet's "4,308 passed" included). It is not in the `verify_orion.ps1` subset.
- **Preconditions:** the owner, or a disposable rig, is streaming while any agent or developer runs the broad suite on the same user account. In the audit phase, several agents were doing exactly that.
- **Failure path:**
  1. The test calls the real sweep.
  2. The sweep finds `OrionStream.exe` and kills it with exit code 1.
  3. The test then `pytest.skip`s, so the suite stays green and the kill is invisible.
  4. The console holds the session (`0x80108b10`) for about 18 s, and the launcher spends about 36 s in recovery plus a second restart.
- **Impact:**
  - Destroys the owner's live play tests and produces false "disconnect" evidence. Two audit rounds attributed this incident to the product; AUD-A3-001 is open on it.
  - Violates the prompt pack's "never force-kill the owner's session" rule by accident.
  - Any hardware or rig session evidence gathered while suites ran in parallel is suspect.
  - There is no customer-package impact: tests are not shipped.
- **Reproduction:** safe, with all kill and snapshot calls faked. `.venv\Scripts\python.exe -B C:\Users\aaron\AppData\Local\Temp\claude-F3\f3_sweep_test_hazard.py` gave `RESULT: test SKIPPED: a chiaki-family process is running here: ['OrionStream.exe:424242']`, `KILL_CALLS_BEFORE_SKIP: [('TerminateProcess(handle, 1)', [424242])]` and `last_sweep_report: {'found': ['OrionStream.exe:424242'], 'killed': [424242], 'failed': [], 'fallback': False}`, exit 0.
- **Field correlation:** the `pt3` tmp dirs at 21:28:52.556 → 21:28:59.5097 local, against the native pipe loss at ≤ 02:28:59.470Z and the sidecar's `exit_code=1` at .520Z (see the incident section).
- **Fix:**
  1. Make the test non-destructive: assert on `_running_image_pids` only, or skip *before* sweeping when `found` would be non-empty. Better, run the sweep against a test-owned image name spawned by the test.
  2. Add a global offline-guard-style fixture that fails any test calling the real `TerminateProcess`/`taskkill` on a PID the test did not spawn.
  3. Mark any real-process test `slow`/`hardware` and exclude it by default.
- **Closure test:**
  - With a harmless dummy process renamed `OrionStream.exe` running under the same user in a disposable VM, `pytest tests -m "not slow"` completes and the dummy is still alive.
  - The new guard fails a canary test that tries to kill a foreign PID.
  - Keep AUD-A3-001's incident "strong hypothesis: test-suite sweep" until one field recurrence carries a ledger `stale_client_sweep` record, or none recurs over N sessions with suites quarantined.
