### CL3-F1-002 MEDIUM: the frozen update manifest cannot be published, so the served manifest is not part of the frozen unit
- **Tier:** fixture reproduction + source-confirmed. **Candidate:** `update_manifest.json` `2652b3d6…`.
- **Preconditions:** publishing 1.0.0 (or later) as an update.
- **Path:**
  - `update_manifest.json` has `"artifact_url": ""`, and `artifact_url` is one of the 8 signed fields (`package_orion_release.py:82-86`; native `UpdateManifest.cpp` `canonicalManifestSigningString`).
  - The backend publish route requires a non-empty `artifact_url` and a pre-signed signature (`backend/lambda_function.py:994-1002`: `missing required field: artifact_url`).
  - Publishing therefore needs a **new offline signature over a different payload**. My negative control shows this: setting `artifact_url` to any HTTPS URL gives `Update manifest Ed25519 signature INVALID`.
  - The manifest that customers' updaters will actually receive has no hash in the candidate sheet and was not reviewed. The ZIP hash, version and key ID are correct and verified.
- **Impact:** a gap in the release-integrity chain of custody. The object a client will trust is created after the freeze. It is not a client bypass: clients still verify Ed25519 and the SHA-256.
- **Reproduction:** `python -c "…verify_update_manifest('um_url.json', None, '<pinned>')"` printed `{'ok': False, 'errors': ['Update manifest Ed25519 signature INVALID (native client would reject)']}`, exit 0.
- **Fix:** run the packager with `--artifact-url https://<owned-origin>/…/orion-package-1.0.0.zip` (it is validated by `_validate_artifact_url`). Alternatively, add the final signed publish manifest, with its SHA-256, to the candidate sheet before the Codex release gate. In either case, refuse to call a triple "frozen" while `artifact_url` is empty.
- **Closure test:** `verify_release_integrity.py … --update-manifest <final> --artifact <zip> --public-key <pinned>` passes, the final `artifact_url` passes `_artifact_url_allowed`, and the sheet lists the final manifest's hash.
- **Rollback:** unaffected. `allow_rollback=false` and `minimum_supported_version=0.0.0`.

### CL3-F1-003 LOW: packager publication survives exceptions but not process death, and has no crash recovery (refines AUD-A6-003)
- **Tier:** fixture reproduction (`a6/crash_fixture.py`, which patches `pathlib.Path.replace` to `os._exit(9)` after N renames. Validation was stubbed for the fixture. The real `publish_release_unit` was exercised on scratch dirs).
- **Component:** `tools/package_orion_release.py:703-770` `publish_release_unit`.
- **Path:** all three old targets are renamed to `.<name>.previous-<token>` **before** any new target is installed. Rollback runs only in `except BaseException`, and a hard kill (power loss, TerminateProcess, `os._exit`) skips it. Unlike `pack_lethe_release.py`, which has `recover_publish_journal`, the packager keeps no journal, and nothing in it references `.previous-` for recovery (`grep` shows only line 733). Literal results:
  - `kill after rename #1: pkg=MISSING zip=OLDZIP man=OLDMAN`
  - `#3: pkg=MISSING zip=MISSING man=MISSING`
  - `#4: pkg=NEW zip=MISSING man=MISSING`
  - `#5: pkg=NEW zip=NEWZIP man=MISSING`
  - Every run leaves orphaned `.previous-<token>` backups. Fixture exit 0.
- **Mitigation observed:** old and new files never coexist at the fixed paths, because all backups happen first. A reader sees *missing* paths, not a mixed signed triple. Clients are protected by the signatures.
- **Impact:** owner build host only. After a crash, `release/` can hold a new package with no ZIP or manifest. `build_installer.ps1` gates only on the package (`pack_lethe --verify-only --input`), so it could still build an installer from a package whose ZIP/manifest triple is incomplete.
- **Fix:** write a journal before the first rename, and replay or undo it on the next run. The logic can be shared with `pack_lethe_release.recover_publish_journal`. Alternatively, adopt the immutable release-unit directory plus an atomic selector (FIXUP_REPORT §84). Make the installer build verify the whole triple.
- **Closure test:** the kill-after-N fixture for N = 1..6, followed by a second packager run, must restore either the complete old triple or the complete new one, with no `.previous-*` left behind.

### CL3-F1-004 LOW: 69 timing and fire-policy env overrides are still live in production AutomationCore, and the gate-record string claim is inaccurate
- **Tier:** source-confirmed + observed strings in the package.
- **Component:** `AutomationEngine.cpp`. A preprocessor-aware scan found 10 fenced env reads (the ONSET_FF family, `ORION_DEV_FIRE_OFFSET_SWEEP`, `ORION_DEV_LATE_CARRY_AB`, `LEAD_FLOOR`/`LEAD_BIAS`) and **69 unfenced**. Examples: `ORION_GREEN_CENTER_FRAC` (line 2620), `ORION_OWNED_METER_NEVER_ABORTS` (1851), `ORION_METER_BLIND_BACKSTOP` (2700), `ORION_PRESS_LATENCY_TRIM_GAIN`, `ORION_METER_TIME_SCALE`, `ORION_BANNER_TRIM_*`, `ORION_HORIZON_DEBIAS`. All are ASCII-present in the shipped `AutomationCore.dll`. The sidecar (inherited environment; `RemotePlaySession.cpp:2371` removes only selected keys) carries about 615 `ORION_*` names, including `ORION_CAPTURE_LEGACY_SCAN`. That flag is honoured but capped at route basis "uncertain" (`capture_card_backend.py:1271-1283`).
- **Preconditions:** the same Windows user sets environment variables. No auth or entitlement effect was found. The blind backstop already defaults to on (`AppConfig.h:1477`), so the env var adds no new fire capability.
- **Impact:** a customer or a same-user process can silently change timing and fire policy with no tamper signal. The support logs will not explain it. This is the same class as M-24, but it was not in M-24's scope. Separately, the sheet row "Production binaries contain no `ORION_LEAD_FLOOR_MS` / `ORION_LEAD_BIAS_MS` strings: verified" is literally false. Both strings exist as UTF-16 message text in `OrionNative.exe` (offsets 2084274/2084318) and in `AutomationCore.dll` (680738). The env *reads* are fenced, so the sheet should say "no env reads", not "no strings".
- **Fix:** put an allowlist in front of the production env reads (compile out all but the documented kill switches), or log every honoured override on the Diagnostics page. Correct the sheet wording.
- **Closure test:** re-run the preprocessor scan, which should show 0 unfenced timing overrides or only allowlisted ones. A production-build unit test with `ORION_GREEN_CENTER_FRAC=0.9` set should show the config unchanged.
