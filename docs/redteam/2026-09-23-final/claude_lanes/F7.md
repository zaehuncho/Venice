# F7: install, update and recovery (Claude internal lane, rc1)

**Lane verdict: blocked.** The signature, hash, key-id, alg, HTTPS, archive-safety and injected-rollback gates all refused fail-closed in the fixture matrix. However, the elevated update path (M-14) is never taken for a default Program Files install. A realistic apply/prune failure can also leave a mixed-version install. In addition, `orion.iss` allows a custom install directory with no ACL hardening, while it registers a LocalSystem service from that directory.

## Findings (LOW → CRITICAL)

### CL3-F7-007: LOW. The installer does not close `OrionStream.exe` and the updater's owner list misnames `VeniceNetSvc.exe`
- Evidence tier: source-confirmed. Candidate: installer `d0383f12…`, updater `838cace7…`.
- `installer/orion.iss` CloseVeniceProcesses names OrionNative, OrionSidecar, OrionUpdater, OrionOwner, OrionStaff and OrionActivate, but **not OrionStream.exe**. An orphaned fork process therefore locks `chiaki-ng-orion\…` during upgrade.
- The `updater_main.cpp:234-238` knownOwner list has `venicenet.exe`, but the shipped binary is `packet_bridge/VeniceNetSvc.exe`. An updater that cannot open a SYSTEM process falls back to that name match, and the name match misses the service.
- The app demand-starts VeniceNetSvc (`OrionAppController.cpp:15881`) and never stops it. An elevated updater would then hit `Install-local process/service did not exit within 30 seconds`. This fails closed, but it blocks the update.
- Fix: add OrionStream.exe to the installer list. Match `venicenetsvc.exe` in the updater. Have the updater stop VeniceNetSvc through SCM, with a checked result, before the ownership barrier.
- Closure test: VM upgrade with an orphaned OrionStream and with a running VeniceNetSvc. The update must apply.

### CL3-F7-006: LOW. Some traversal entries are refused only by accident
- Evidence tier: fixture reproduction (C14/C17/C18).
- QZipReader normalises the `../`, leading `/` and `..\` names, so the traversal pre-check passes. The entry is then refused as "truncated or corrupt (declared 1, read 0)". This fails closed today, but it depends on a Qt reader quirk.
- Fix: validate the raw central-directory names (reject `..`, a leading `/` or `\`, drive letters, backslashes and NUL) before any normalisation.
- Closure test: C14/C17/C18 must log `path traversal`.

### CL3-F7-005: MEDIUM. A signed ZIP can install runtime files that are not in its signed release manifest
- Evidence tier: fixture reproduction (C20). Component: `SecurityManager::verifyReleaseIntegrity(exactRoot)` (`SecurityManager.cpp:578-610`) checks listed files only; `applyTree` copies every staged file.
- Preconditions: a publisher or pipeline mistake. An attacker cannot do this without the signing key.
- Impact: unmanifested DLLs, including Qt plugin directories such as `platforms/`, land in the install. This is the "unmanifested runtime files" release-blocker class, reached through the update channel. Stage cleanup was also still pending at the check time in this run (`.orion_updater_stage-wnQyJh` left).
- Fix: after extraction, refuse any staged file not in the new signed manifest, apart from the manifest and signature themselves.
- Closure test: C20 must be refused, with the install unchanged.

### CL3-F7-004: MEDIUM. The downgrade gate trusts the caller's `--current-version`
- Evidence tier: fixture reproduction (C25) plus source (`updater_main.cpp:414`, `UpdateManifest.cpp:265`); the production code path is the same.
- Preconditions: a previously published, genuinely signed older manifest and its artifact still exist. The attacker must also be able to start the updater with install write access, meaning a UAC consent to the genuine-looking `OrionUpdater.exe` or a user-writable install (CL3-F7-003). `--manifest-url` accepts any HTTPS host in production.
- Impact: rollback to an older signed build with known flaws. There is no exposure at 1.0.0 because no older production manifest exists; the risk starts with the first update.
- Fix: derive the current version from the verified installed `release_manifest.json` `version` (or the updater's compiled version), ignore the CLI value, and pin the manifest host in production.
- Closure test: C25 must be refused, and a production `--manifest-url` pointing at a non-pinned host must be refused.

### CL3-F7-003: HIGH. A custom install directory is allowed with no ACL hardening, while a LocalSystem service and its driver DLL run from it
- Evidence tier: source-confirmed, plus parent-ACL observation. Component: `installer/orion.iss` [Setup]. There is no `DisableDirPage`, so the Inno default shows the directory page on first install. There is no `[Dirs]` Permissions entry and no custom-path check.
- `RegisterPacketBridgeService` creates `VeniceNetSvc` with `obj= LocalSystem` and binPath `{app}\packet_bridge\VeniceNetSvc.exe`, which loads `WinDivert64.dll` beside it. The SDDL grants Interactive Users start/stop.
- Preconditions: the customer chooses a directory under a user-writable parent. On a Windows secondary NTFS drive root such as `D:\`, or `C:\` itself, Authenticated Users inherit Modify on new subfolders by default. Not verified on this PC: `D:` is absent and nothing was installed.
- Impact: any standard-user process can swap the service EXE or DLL and then start the service. That is SYSTEM code execution, a privilege-boundary break and a release blocker. The owner's default Program Files install is not affected (`icacls "C:\Program Files"` shows Users `(RX)` only).
- Related data-loss issue: `[UninstallDelete] filesandordirs {app}` deletes the whole chosen folder. If a user types an existing folder (for example `D:\Games`) and clicks through the "folder exists" warning, uninstall erases unrelated files there.
- Fix: set `DisableDirPage=yes` (as UPDATER_CLIENT.md already claims: "The installer fixes the install directory under Program Files"). Alternatively, reject any directory outside `{autopf}` and apply an explicit `[Dirs] {app}` ACL of Admins/SYSTEM full and Users RX. Delete only the files the installer tracked, plus named runtime files.
- Closure test (VM): after install, `icacls` on `{app}` and `{app}\packet_bridge` must show no Users/Authenticated Users write access. `sc qc VeniceNetSvc` must show a binPath under Program Files. The installer must refuse `D:\Venice`. Uninstall must not remove a pre-existing sibling file.

### CL3-F7-002: HIGH. A realistic prune/apply failure leaves a mixed-version install ("rollback failed")
- Evidence tier: fixture reproduction (C27, C28). Component: `UpdaterArchive.cpp:224-229` (unconditional remove-before-copy, including during restore) and `restoreTree` (`:588-601`), which stops at the first failing entry.
- Preconditions: any foreign handle without share-delete on one runtime file, such as antivirus, a backup or indexer tool, or an orphaned process that the barrier misses. The barrier checks only process images and modules, not open file handles.
- C27 literal result: after the fault, `Qt6Core.dll`, `UpdaterCore.dll`, `release_manifest.json` and `release_manifest.sig` were NEW while the rest was OLD; digest `c748b31e2c5f92cb` versus the old `f9070139d93fb044`. Integrity then fails at launch and automation locks, so a reinstall is required. A6-001's self-lock is fixed (C26 exact rollback), but the underlying "restore hits the same lock" pattern remains for foreign locks.
- C28 left the install exact, but still reported "Reinstall may be required".
- Fix: in restore, skip entries whose hash already equals the backup and continue past failures; use rename-aside or `MoveFileEx(REPLACE_EXISTING|WRITE_THROUGH)` instead of delete-then-copy; retry with backoff on sharing violations; perform the prune before overlay (or as rename-aside); on residual failure, keep the durable backup and a recovery marker that the next launch or installer repair can finish.
- Closure test: repeat C27/C28 with the lock held through the whole run and with the lock released after 5 s. The final inventory must equal the exact old hashes (or the exact new hashes), never a mix.

### CL3-F7-001: HIGH. M-14 is still open: the launcher never requests elevation for a Program Files install, so updates cannot apply for any customer on the default install
- Evidence tier: fixture reproduction with a Qt 6.8.0 probe mirroring the exact expression, plus packaged-manifest observation.
- Component: `OrionAppController.cpp:5874-5877` uses `QFileInfo(installDir).isWritable() && QFileInfo(parent).isWritable()`. Qt's NTFS permission lookup is disabled by default, and no code in `native_orion` enables it. The check therefore reads attributes, not ACLs. Both packaged EXEs are `requestedExecutionLevel level='asInvoker'`.
- Reproduction (medium integrity, not admin): `claude-F7\qtprobe\probe.exe "C:\Program Files\Venice" …` returned:
  ```
  C:\Program Files\Venice dir=1 parent=1 installDirWritable=1 elevationRequested=0
  C:\Windows\System32\drivers dir=1 parent=1 installDirWritable=1 elevationRequested=0
  qt=6.8.0
  exit=0
  ```
  `icacls "C:\Program Files"` shows `BUILTIN\Users:(RX)`.
- Failure path: no `runas` call, so a plain `startDetached` runs. The first stage cannot create `C:\Program Files\.orion_updater_stage-*`, so it fails with "Could not stage updater outside install". The launcher's no-lockout guard then continues on the old version. This is fail-closed and nothing is modified. UAC admins also run at medium integrity, so they are affected too.
- Impact: optional, mandatory and emergency (key rotation / compromised-build) updates never install on default installs. The recovery procedures in UPDATER_CLIENT.md ("publish mandatory update") do not work in the field.
- Fix: decide elevation by an actual write probe (for example, create and delete a uniquely named temp file in the parent directory) or with `QNtfsPermissionCheckGuard`, or give OrionUpdater a `requireAdministrator` manifest. Keep the no-lockout guard.
- Closure test: owner VM standard user, and an admin with UAC. A signed update must show a UAC prompt, then apply, then relaunch, with exact new hashes. Decline must leave the install unchanged and the app running.

## Other observations (not findings)
- The frozen `update_manifest.json` has `"artifact_url": ""`, so the updater would refuse it (`Artifact URL is not HTTPS`). The deployable manifest will be re-signed with a URL after the freeze, which means the exact signed update record is not part of rc1. The owner must hash-record the published manifest.
- The unsigned `public_key_b64` field in that manifest is ignored by the parser (trust comes only from the embedded key; `UpdateManifest.cpp:160-173`).
- Uninstall data policy: `%LOCALAPPDATA%\NexusVision\Orion Native` (settings, learning, logs, calibration) is kept by default. Removal happens only on an interactive "Yes" (default No) and never in silent mode. The bridge tokens are removed. The elevated-profile `{localappdata}` caveat is documented. Leftovers not covered by uninstall: `…\Program Files\.orion_update_backup` and any `.orion_updater_stage-*` siblings.
- Drivers: ViGEmBus 1.22.0 (upstream retired) and HidHide 1.5.230 are installed only when the service key is absent. There is no minimum-version check, so an older ViGEmBus already present is accepted. NeedRestart/RestartPending correctly cover 3010 from the drivers and the VC++ runtime, and the launch checkbox is hidden while a restart is pending.
- `PrivilegesRequired=admin` (per-machine install); a standard user needs admin credentials.
