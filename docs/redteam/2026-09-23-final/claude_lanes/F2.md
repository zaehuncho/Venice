## Owner live evidence: Square "stuck" (09-23 12:02–12:23 local = 17:02–17:23Z)

- The pipe owned input for the whole session (`Controller route isolation: direct Chiaki pipe owns PS5 input; desktop XUSB held neutral.` at 17:02:36.702Z). No fallback flip happened. `failures=0 ack_failures=0 abandons=0` through the last heartbeat (`writes=40789`).
- Flagged Square packets: 46 with `btn=4`. Every Square hold in the fork log ends with a `btn=0` packet that was ACKed `stage=2`. The longest were seq 821→834 (1,249 ms), 2454→2497 (1,175 ms) and 579→590 (1,155 ms). All had `own=1` and matched human pass-through holds (`IDLE-GATE … waiting_for_genuine_meter_before_ownership`).
- Square re-sends: `targets=0x00004` stage 1 = 39, stage 5 = 34. The 5 missing stage-5 series were cancelled by a new Square DOWN, which is expected.
- In all 25 bot-owned shots the console was told Square-up while the human still held it: `Release ownership … max_out_sq=0 out_cleared_all=1 out_diverge_events=0` (25/25), and `SQUARE SUPPRESSED … (physical Square held; console being told Square-up)`. **No re-press after a bot release** was found.
- The Qt second producer (M-32) enqueued **0 times**: `grep -c 'edge_enqueued source_seq=0 '` returned `0`.
- Chiaki opened only `Xbox 360 Controller` (the ViGEm pad). The DualSense is excluded from SDL (`remote_play_client.py:921-925`). The SDL merge is skipped while the bridge owns input (`streamsession.cpp:1392`).
- **Conclusion:** the PC-side input stream shows no held Square. Two things are **not verified**: whether the console received it (no console ACK exists) and the in-game mechanic (for example, the long human holds of 1.0–1.25 s). The only PC-side "held" contributors found are bounded: the 151 ms tick stall and a 24–50 ms debounce tail on 5 of 41 human Square-ups (most were 7–10 ms).

## Findings (LOW → CRITICAL)

### CL3-F2-002 LOW: Qt keep-alive is still a second producer that can re-press a released button (M-32 residual)
- **Tier:** source-confirmed; not observed live (0 occurrences). **Candidate:** fork `67eec725` / rc1 `OrionStream.exe` `1f659a46`.
- **Component:** fork `gui/src/streamsession.cpp:1392-1407` reads `orion_bridge->currentState()` under the bridge lock and then calls `chiaki_session_set_controller_state_nowait` (seq 0, flags 0) **outside** it. `gui/src/orioninputbridge.cpp` publishes `state_` and then calls `set_state_nowait_ex` as a separate step. `feedbacksender.c:249-257` edge-detects against `orion_pending_state`.
- **Preconditions:** the bridge owns input, the keep-alive is allowed, and a ViGEm `StateChanged` fires on the Qt thread in the µs window between the snapshot and the bridge's release enqueue.
- **Failure path:** snapshot (Square held) → bridge enqueues Square-up → keep-alive enqueues the stale held state as a new unflagged edge → the console sees Square pressed again until the next bridge packet (≤~100 ms owned keep-alive).
- **Impact:** a phantom re-press or pump fake. It does not stay stuck.
- **Reproduction:** `grep -a -c 'edge_enqueued source_seq=0 ' <chiaki log>` returned `0`, exit 0. So the path is **not observed**; no race fixture exists.
- **Fix:** drop the Qt keep-alive while the bridge owns input (the launcher's owned keep-alive plus the bridge path already cover it), or do the snapshot-and-enqueue under one lock with a generation check.
- **Closure test:** a fork unit test interleaves a release with a stale keep-alive and asserts that no DOWN follows the UP.
- **Rollback:** none needed.

### CL3-F2-003 LOW: On pipe loss the launcher mirrors gameplay onto the desktop XUSB pad for 100–170 ms, and the log says the fallback "carries PS5 input"
- **Tier:** observed in logs. **Candidate:** launcher source `59129e5` (the rc1 launcher contains the same code).
- **Component:** `OrionAppController.cpp:13880-13898` and `:14234-14238`. `hookOwnsInput` goes false as soon as `orionInput_.connected()` drops while `directInputReady` is still true, which happens before `inputRecoveryPending` is set.
- **Evidence:**
  - `02:28:59.470Z … direct pipe unavailable; ViGEm/XUSB fallback carries PS5 input.` was followed by `02:28:59.584Z Input-only recovery started` (114 ms).
  - On 09-22 03:11:12.552 → 03:11:12.720 (168 ms) the same happened, and the timing route was even re-attested (`Timing route acknowledged directly by sidecar: route=vigem_xusb`).
  - There were 11 such flips in `orion_native.log(.1)`.
- **Impact:** during that window the fork is dead or holds ownership latched, so the console receives none of it. The only consumer is the Windows desktop through XInput/WGI: a brief window where the stick can drive whatever PC window has focus. Held Square or R2 is mirrored onto the desktop pad until neutralized.
- **Fix:** once the pipe has owned input in this session, keep XUSB neutral until an explicit fallback decision. Also make the log say "input unavailable" rather than "fallback carries PS5 input".
- **Closure test:** a controller fixture drops the pipe while Running and asserts that every ViGEm submit before the recovery verdict is neutral.

### CL3-F2-004 LOW: Evidence lines mislead stuck-input triage
- **Tier:** observed. Three defects:
  1. **Square-up audit contradicts the fork.** `Square-up route audit … current_delivery_stage=not_confirmed snapshot_local_ack=0` was logged for 25 of 41 epochs. For seq 600 the fork shows `ack_local_delivery source_seq=600 stage=2` plus 2 history copies. The snapshot uses the last de-duplicated `lastSent()` (`OrionAppController.cpp:13935-13943`). This made the owner's report look like an unconfirmed release.
  2. **UI isolation log is uninformative.** `Controller UI isolation active` is logged once per process with no message kind or origin (`OrionAppController.cpp:5404-5408`), so the "hover" cannot be attributed.
  3. **Normal quit is classified as fatal.** The fork classifies an ordinary application quit (neutral ACKed, then the pipe closes) as `Orion exit_path: source=orion_bridge_fatal detail=owner_pipe_disconnected`, which pollutes AUD-A3-001 exit classification.
- **Fix:**
  - Join the audit to the release transaction's own seq and ACK stage.
  - Log the kind, origin and foreground process for each suppressed burst (rate-limited).
  - Have the launcher send the `own=0` ownership barrier (or a "clean close" ABANDON) before a graceful close, and classify that as clean.
- **Closure test:** replay today's log shape so that the audit shows `local_udp_accepted` for bot releases, and a graceful quit yields a clean exit classification.

### CL3-F2-001 MEDIUM: Production-profile route-transition fixture fails; StrictSecurity likely red
- **Tier:** fixture reproduction on a production build of the same source. **Candidate:** `build_prod_review` (`ORION_PRODUCTION=ON`), source `59129e5`.
- **Component:** `native_orion/tests/RouteTransitionIntegrationTests.cpp:179,248` and `RemotePlaySession.cpp:2271-2285`. In a production build the sidecar launcher requires `models/orion_meter_detector.onnx` beside the test EXE and sets `Error` without launching the fake producer.
- **Impact:**
  - AUD-A2-001/002 transition safety (warm A→B cold start, refusal while a shot is live) is **unproven in the shipping profile**. The dev pass alone does not exercise the production sidecar launch path.
  - `scripts/verify_orion.ps1 -StrictSecurity` builds `OrionRouteTransitionTests` in `native_orion\build_prod_codex` and runs `Invoke-OrionNativeTests` there. It will very likely report 2 failures.
- **Reproduction:** `& build_prod_review\a2_route_fixture\Release\OrionRouteTransitionTests.exe -o …,txt`, with the PATH set to `build_prod_review\Release` and the Qt bin, and offscreen QPA. Result: `Totals: 3 passed, 2 failed`, exit 2. The dev-profile control gave `5 passed`, exit 0.
- **Fix:** stage a dummy detector model in the fixture's `models/` directory (a POST_BUILD copy) or add a test seam for the model root. Do not relax the production check.
- **Closure test:** prod-profile `OrionRouteTransitionTests` 5/5 plus a green StrictSecurity transcript.
- **Rollback:** none needed. The product behaves correctly (fails closed); only the fixture is wrong.

No HIGH or CRITICAL findings in this lane. **Immediate-blocker summary:** none from input behaviour. CL3-F2-001 blocks the StrictSecurity gate until the fixture is fixed or the failure is dispositioned.
