## Ranked findings — lowest to highest

### P7-01 — LOW — preview shared-memory object permissions are implicit; live ACL unmeasured — needs changes

- **Path / affected:** `shm_frame_bridge.py:203-243` creates a named mutex, mapping, and event with default Windows security attributes; `native_orion/src/SharedMemoryFrameReader.cpp:87-118` reads the mapping. Names are generated per session (`RemotePlaySession.cpp:3351-3358`), but are not an authorization secret.
- **Impact:** Another process under a permitted Windows SID could potentially open or interfere with preview objects. The preview path is display-only here; I found no proof that altering this mapping alone grants shot/fire authority. The cross-user ACL and actual object owner were not measured.
- **High-level reproduction:** On an isolated, non-console preview fixture, inspect the live mapping/mutex/event DACL under the launcher account and a second standard account; attempt read/write/open without sending game input.
- **Required fix:** Specify and verify the intended owner/SYSTEM DACL, use unpredictable per-session names only as collision protection, and treat every mapped header/pixel as untrusted. Do not promote preview data to detector authority.
- **Verification:** The owner can read; a second standard account cannot; corrupted headers are rejected without crash or automation; preview recovers after object loss.

### P8-01 — MEDIUM — suspend/restart disruptions have fixture coverage but no complete physical-state proof — needs changes

- **Path / affected:** session/input recovery (`native_orion/src/RemotePlaySession.cpp:3690-3740`, `remote_play_orchestrator.py:3236-3320`), lease freshness (`native_orion/src/LeaseGate.cpp:14-28,84-95`), service/driver teardown. Wi-Fi drop, console rest, hibernate, and Windows-update reboot are distinct transitions, not one generic reconnect.
- **Impact:** A paused process or abruptly replaced network/USB stack could wake with stale ownership, a held button, stale telemetry, or a stale service handle. I did **not** reproduce such an end-to-end failure here; this is an unclosed release test gate, sharpened by the separately confirmed recovery issues P8-03 below.
- **High-level reproduction:** On a controlled rig, suspend/hibernate during physical hold, scheduled-fire wait, input-pipe recovery, and service packet delay; separately drop Wi-Fi, enter console rest mode, and reboot for a Windows update. Record the last pre-event and first post-event arm token, lease, route, held-output, and service state.
- **Required fix:** Explicit wake/session-generation invalidation and re-attestation before any post-resume fire; release/neutralize old ownership on bounded failure; make update/reboot recovery transactional.
- **Verification:** No stale command reaches a fresh session, the first post-resume shot requires fresh video/input/lease proofs, and the human regains ordinary input on timeout.

### P6-01 — MEDIUM — lead-calibration cancel does not preserve the original Auto/zero state — needs changes

- **Path / affected:** `native_orion/src/OrionAppController.cpp:9185-9213`. The start value is captured, but cancel restores it only if `leadCalStartLeadMs_ > 0`; otherwise it reads the **current** `actuationLeadMs()` after graded steps.
- **Impact:** A customer entering calibration in Auto/zero mode can cancel after a graded step yet retain a changed effective lead or lose the original Auto provenance. That is quiet per-customer timing drift, not merely a cosmetic status issue. The positive-value rollback path is covered; this path needs a test.
- **High-level reproduction:** In an isolated config/profile fixture, start at Auto/zero, accept a graded calibration step, cancel, and compare both effective lead and Auto/manual state against the pre-calibration snapshot.
- **Required fix:** Snapshot and restore the exact mode plus value, not a `>0` numeric surrogate; persist cancellation atomically.
- **Verification:** Auto/zero, positive manual lead, zero-shot cancel, and repeated cancel all restore exactly; a completed calibration retains the intended new value.

### P6-02 — MEDIUM — production timing experiments remain environment-selectable — needs changes

- **Path / affected:** `native_orion/src/AutomationEngine.cpp:1602-1655,17597-17677`; `native_orion/src/AppConfig.h:1290-1312`. The shipped onset feedforward defaults to gain 0.2/clamp 10 ms. `ORION_ONSET_FF_AB` and the tuning env variables are parsed without a production-build guard; the A/B can select up to 40 ms clamp. By contrast, `ORION_DEV_LATE_CARRY_AB` is guarded at `AutomationEngine.cpp:1661-1683`, and the sweep parser at `:17276-17350` is production-guarded.
- **Impact:** Local environment/configuration can put a customer on an unapproved timing arm. This is not an auth bypass; it is an unintended production experiment/control surface and can contaminate diagnosis of a real drift incident.
- **High-level reproduction:** Launch an isolated production-build fixture with only the onset A/B env set, take synthetic scheduled-fire decisions, and compare arm selection/deadline to a clean process. Do not infer behavior from the dev test binary alone.
- **Required fix:** Compile out or signed-policy-gate experimental A/B in production; separate approved bounded default from an explicit operator experiment; log exact arm/build identity in diagnostics.
- **Verification:** Production ignores all experiment env values while the approved default remains bounded; dev A/B covers arm parsing, session reset, and learner fences. The 2026-09-22 `+10 ms` confirmation in `docs/variance/OFFSET_SWEEP_RESULT_2026-09-22.md` **refuted** a global +10 ms bias (101/arm; 76.2% at 0 vs 56.4% at +10; difference -19.8 pp, 95% interval [-31.9,-6.8]); do not ship that fixed shift. The 0.20-vs-0.45 onset A/B was uninformative, not proof of benefit.

### P8-02 — MEDIUM — multi-device capacity is a single mutable binding, not simultaneous seats — needs changes if multi-device licences are sold

- **Path / affected:** `backend/lambda_function.py:745-795,1774-1788`. The atomic bind prevents two first activations winning `max_devices=1`, and the second machine is rejected in `tests/backend/test_activate.py:26-33`. But when `max_devices>1`, each successful bind overwrites one `machine_id`; heartbeat then compares against that one value.
- **Impact:** For a multi-device entitlement, PC B can displace PC A rather than both remaining licensed. The default one-device case is not bypassed in the fixture tests; this is a product/entitlement correctness issue, not evidence of a two-PC bypass of `max_devices=1`.
- **High-level reproduction:** Use a nonproduction licence row with capacity two; activate A then B, heartbeat both, and observe which machine remains bound.
- **Required fix:** Either document/enforce single-device only or store a bounded set of machine bindings with atomic per-seat claims and revocations.
- **Verification:** Capacity one denies B, capacity two keeps A and B valid, capacity three rejects D, and concurrent claims never exceed capacity.

### P6-03 — HIGH — learning-file “last good” can be semantic garbage or be lost during backup rotation — needs changes

- **Path / affected:** `native_orion/src/AppConfig.cpp:96-116,270-302,1254-1275`; `native_orion/tests/AutomationEngineTests.cpp:47279-47350` covers zero-byte recovery only. `readObjectStatus` accepts any nonempty JSON object as “valid,” and backup removal/copy, quarantine rename, and restore copy return values are not checked. Quarantine names have only second resolution.
- **Impact:** A syntactically valid but incomplete/poisoned learning file can replace the known-good backup; a failed copy can leave no verified last-good generation; rapid repeated corruption can collide with a quarantine name. On next launch, timing can silently reset or load bad but in-range values for every subsequent shot on that customer profile.
- **High-level reproduction:** In a disposable profile, seed known learned values, then present `{}` and a structurally valid object with missing/invalid learner fields; separately make backup copy fail and corrupt twice within one second. Compare restored values, file hashes, note truthfulness, and saved backup. No live customer file should be touched.
- **Required fix:** Validate a versioned learning schema and semantic ranges before promotion; write/verify a new backup before replacing the old one; check every filesystem result; use unique quarantine naming and fail closed on unrecoverable ambiguity.
- **Verification:** Crash-mid-write, `{}`, malformed-but-parseable fields, backup-copy failure, collision, and profile-specific learning files all preserve the last verified generation or visibly refuse to learn. The current happy-path tests do not establish this.

### P7-02 — HIGH — a second same-user process can issue controller packets to the fixed input pipe — blocked

- **Path / affected:** fork `gui/include/orionpipesecurity.h:51-67` allows SYSTEM, admins, and the current user SID full access; fork `gui/src/orioninputbridge.cpp:113-144,179-255` accepts the first pipe client and treats a public packet magic as its only packet check; launcher `native_orion/src/OrionInputClient.cpp:205,346-353` connects to the fixed `\\.\pipe\orion_input` and verifies ACK shape, not server identity. The pipe creation lacks `PIPE_REJECT_REMOTE_CLIENTS` and first-instance enforcement.
- **Impact:** **Yes, another program running as the same Windows user can, by this design, race the launcher for the live pipe and submit `own/buttons/sticks` packets to the fork, which forwards them to the console session.** The ACL does exclude a different ordinary local SID in source. A same-user process can also pre-create the known pipe name and impersonate the server to the launcher; a shaped ACK does not prove the real fork accepted a command. These are source-level findings; no console command was sent in this audit.
- **High-level reproduction:** With a dummy, isolated fork/input fixture and no real console, start the fork pipe server, connect a second same-SID process first, submit benign synthetic controller states, and verify they reach the dummy sink. Repeat from another SID and with a fake pre-created pipe server; record rejection/identity result.
- **Required fix:** Authenticate the peer/session, bind it to the launched process generation (not just user SID or public magic), use an unpredictable per-session endpoint passed through a protected launch channel, reject remote clients, and reject pipe-name squatting/peer impersonation. Preserve human passthrough when authentication fails.
- **Verification:** Correct launcher generation alone can control; a same-user unrelated process, another SID, stale generation, and fake server are rejected without buttons or a false “delivered” result. Test the **packaged** `OrionStream.exe`, not just fork source.

### P7-03 — HIGH — all Interactive Users can read the elevated service bearer token — blocked

- **Path / affected:** `native_orion/venicenet_service/IpcServer.cpp:141-152` and legacy `nexus_svc.py:195-236` grant `(A;;FR;;;IU)` to the service-mode token file; the service listens on loopback port 47291 (`IpcServer.h:7-17,49-50`), accepts the token (`IpcServer.cpp:697-731`), then offers `set_filter`, `set_court_ip`, `start/stop_meter_intercept`, and `set_meter_delay` (`:733-833`). `installer/orion.iss:570-603` runs the service as LocalSystem and grants Interactive Users start/stop/query on the service object.
- **Impact:** A second logged-in local user may read the bearer token and drive the privileged packet-intercept/delay function across user sessions. The command vocabulary and WinDivert filter are constrained (`MeterDelayIntercept.cpp:501-513`); I found **no arbitrary file write or command-execution primitive**, so this is **not proof of gaining an admin shell or full admin rights**. It is still a cross-user privilege-boundary failure. The installed DACL and service binary directory ACL remain unmeasured because the services are absent here.
- **High-level reproduction:** On a throwaway clean Windows install, sign in two standard users; from user B, check ProgramData token-read ACL, loopback auth, allowed command effects on user A’s isolated test traffic, and SCM start/stop. Also inspect `sc sdshow`, `sc qc`, `icacls` on the service binary, directory, token, and driver.
- **Required fix:** Use a per-logon-user authenticated broker channel or bind requests to the intended client SID/process/session; do not make one bearer credential readable by all `IU`. Retain a narrow command schema and separately protect the service image/driver directory from ordinary-user writes.
- **Verification:** User A’s app works; user B cannot authenticate or alter user A’s service state; ordinary users cannot replace the service binary/configure the service; SYSTEM/admin maintenance and uninstall still work.

### P8-03 — HIGH — normal second-launch path does not enforce the launcher singleton — needs changes

- **Path / affected:** `native_orion/src/main.cpp:338-349`. The `Local\OrionNativeLauncher` mutex only causes exit when a **deep link** is being forwarded. For an ordinary second launch, execution continues even when `alreadyRunning` is true. Input pipe name is fixed (`remote_play_client.py:909-911`), learning/settings paths are shared per user (`AppConfig.cpp:249-267`), and both launchers can address the one service endpoint.
- **Impact:** Two ordinary Venice instances are allowed to contend for the same console/client, pipe, service, and learning file. Actual double-control or file corruption was not reproduced; the missing singleton decision is directly visible in source. This also complicates coexistence with the official Remote Play app, which needs a separate controlled rig test rather than process-name guesswork.
- **High-level reproduction:** Launch two copies from a copied, network-isolated package (not from the active dev tree), without a deep link, and count processes, child processes, pipe ownership, service commands, and profile writes.
- **Required fix:** Define one owner per user/session with a clear second-launch UX; bind child/pipe/service identities to that owner; serialize profile writes. Treat a separate official client as an external occupancy condition and show an actionable error, not an invisible retry loop.
- **Verification:** The second launcher raises/focuses the first and creates no second child or writer; a stale mutex from a crash does not block recovery; an occupied console produces a bounded, honest failure.

### P8-04 — HIGH — unresolved input soft-fault and telemetry-silence cases become customer disruption paths — blocked

- **Path / affected:** fork `gui/src/orioninputbridge.cpp:298-310` retains ownership on local-delivery timeout, drops the queue with unchecked result, and re-listens; earlier final gate `RED_TEAM_REPORT.codex.final.md` CL-001/CL-005/CL-006. Native `RemotePlaySession.cpp` has a bounded 20-second input recovery command, but the bridge can repeatedly soft-fault while session ownership stays latched. Independent pipe liveness does not prove that all stale telemetry values have a receipt deadline.
- **Impact:** During Wi-Fi loss, sleep/resume, or a console rest/reconnect transition, the human can remain deprived of passthrough longer than the intended bounded recovery, or a live-but-silent sidecar can look healthy from cached telemetry. This is a failure path, not an authorization bypass; the earlier gate has the detailed packet-level evidence.
- **High-level reproduction:** In a dummy transport test, force repeated delivery timeouts, a failed queue drop, and a sidecar that keeps its pipe but stops JSONL telemetry; observe ownership, neutral state, timer transitions, and final human input.
- **Required fix:** Bound the soft-fault streak and fail to a demonstrably neutral/human-owned state or a full session stop; independently timestamp telemetry receipt; make sender exits observable to the session owner.
- **Verification:** Every injected fault sequence reaches a terminal state within a documented budget, no stale bot command wins, and physical control resumes or the session visibly disconnects.

### P9-01 — HIGH — detection health is local UI only; fleet patch detection is unbounded — needs changes

- **Path / affected:** `simple_meter_reader.py:8081-8111` counts calls/found/locks/drops; `native_orion/backend/autogreen_sidecar.py:826-854,2933-2945` emits `detector_health` every ~2 s; `OrionAppController.cpp:11435-11470` formats a display line. `/api/admin/metrics` (`backend/lambda_function.py:4706-4798`) contains licensing/staff/version metrics, **not detector success, false-lock, or shot-eligibility metrics**. `OrionAppController.cpp:11473-11534` raises `METER BLIND` only after three *completed* meterless epochs, evaluated on a later epoch; QML shows `WATCHING` before that (`MeterConfigPanel.qml:157-185`). Any false raw detection immediately clears the streak. `AutomationEngine.cpp:21889-21903` suppresses the meter-path blind backstop under its current green-window-priority setting, which is a useful fail-closed behavior for absent meters; it does not detect a **wrong** meter/false lock.
- **Impact:** If a game patch changes the meter, the owner has no measured fleet lock-rate alarm in this code path, so time-to-notice is whatever customer reports provide. The local state is late and cannot identify false-lock regressions. “Detection unavailable” is not a first-shot explicit machine state; silent non-release or wrong-lock releases remain possible customer outcomes, not demonstrated live outcomes here.
- **High-level reproduction:** Replay held-out pre-patch and altered-meter/false-lock fixture video through the packaged detector; inspect per-shot UI state and fire authority, then look for any backend aggregate metric/alert with build/game/style dimensions.
- **Required fix:** Add privacy-minimal opt-in/appropriate fleet aggregates with denominators (eligible shot, genuine lock, refused, false-lock proxy, detector exception) and alert thresholds; surface an explicit `detection_unavailable` state from bounded shot evidence and disarm automation on low confidence. Keep the no-meter mode distinct.
- **Verification:** A synthetic patch regression alerts within a stated number of affected eligible shots/minutes; dashboard shows rate by build/style; first affected customer sees an actionable state before repeated misses; false-lock footage never triggers auto-fire.

### P9-02 — HIGH — emergency update turnaround is not proven; default install is unwritable to the unelevated updater — blocked

- **Path / affected:** installer `installer/orion.iss:87,91-92` defaults to `{autopf}\Venice` with admin install. `native_orion/src/updater_main.cpp:220,344-355` writes its log, backup, and applied tree under/near that install directory. `OrionAppController.cpp:2510-2539` rechecks every 30 minutes and defers auto-apply while streaming; `:5515-5539` explicitly documents an unelevated Program Files update failure and falls back to the old version after a failed attempt. Backend `/api/update` accepts only signed manifests and approved HTTPS URLs (`backend/lambda_function.py:957-1036`), but source tests do not establish an installed update turnaround.
- **Impact:** A meter-breaking game patch can be noticed late (P9-01), then the first mandatory update may fail for ordinary customers. The fallback avoids a relaunch loop but does not put the fix on their machine; version blocking can instead lock them out. No measured detect-to-signed-publish-to-installed-fix SLO exists.
- **High-level reproduction:** On a clean standard-user Windows VM, install via the normal elevated installer into Program Files, publish a test signed update to an owned isolated endpoint, run as the standard user, and measure the download, signature/hash, backup, apply, rollback, relaunch, and log paths. Repeat mid-stream and after a forced failed apply.
- **Required fix:** Choose a privilege-correct update architecture (trusted elevated broker/service with narrowly scoped signed payload, or a genuinely per-user install), persist update logs to a writable protected location, and exercise rollback. Document a signed emergency publish/rotation drill and target turnaround.
- **Verification:** Normal nonadmin customers install the test update without manual elevation; tampered/unsigned/wrong-hash packages never apply; failed apply restores the exact prior tree and reports a durable error; a mandatory update has a tested recovery route.
